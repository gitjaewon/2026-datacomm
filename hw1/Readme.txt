2. 프로그램 구성요소 설명
--------------------------------------------------------------------

Master (1개 프로세스, 외부 클라우드 서버(AWS)에서 실행)
  - KVStore            : 5,000개 (key,value) 생성 및 진행 상태 관리
                          (pendingQueue / priorityQueue / store)
  - WorkloadScheduler   : 다음 작업을 어느 Worker에게 보낼지 결정
                          (Least Queue First 알고리즘, 4장 참고)
  - VirtualClock        : Master의 가상 시계
  - FileLogger          : Master.txt 기록
  - ClientHandler x4    : Worker 1개당 1개, 소켓 읽기 전담 Thread

Worker (1개 프로세스 = WorkerLauncher, 조원 로컬 PC에서 실행,
        4개 Worker Node = 4개 Thread)
  - WorkerThread x4     : Worker Node 1개 = 독립 Thread 1개
       - MasterLink      : Master 소켓 "읽기" 전담 보조 Thread
       - P2PServer       : 다른 Worker의 P2P 요청을 받는 보조 Thread
       - ReadyQueue      : 최대 10개 대기 버퍼 (synchronized)
       - VirtualClock    : 이 Worker만의 가상 시계
       - FileLogger      : WorkerN.txt 기록

통신 구조
  - Master <-> Worker      : TCP 소켓 (Master가 accept, Worker가 connect)
  - Worker <-> Worker(P2P) : TCP 소켓 (각 Worker가 자기 포트 6001~6004에
                             P2PServer를 띄우고 서로 클라이언트로 접속)
  - 모든 메시지는 한 줄 텍스트로 직렬화: TYPE|key1=value1|key2=value2|...
    (TASK, RESULT, QUEUE, STATS, REGISTER, SHUTDOWN,
     P2P_QUERY, P2P_STATUS, P2P_TRANSFER, P2P_ACK)

--------------------------------------------------------------------

[공통] 저장소 받기
  git clone https://github.com/gitjaewon/2026-datacomm.git
  cd 2026-datacomm/hw1

[공통] 컴파일 (Master 서버, Worker PC 양쪽 모두 각자 실행)
  * Linux / macOS / Git Bash:
      javac -d out $(find src -name "*.java")
  * Windows PowerShell:
      javac -d out (Get-ChildItem -Recurse -Filter *.java src |
        Select-Object -ExpandProperty FullName)

[Master 서버(AWS)] 실행
  java -cp out kvstore.master.Master <포트번호>
  예) java -cp out kvstore.master.Master 5000

  실행 후 "Waiting for Worker connections." 로그가 뜨면 대기 상태.

[Worker PC(로컬)] 실행
  java -cp out kvstore.worker.WorkerLauncher <Master의 공인IP> <포트번호>
  예) java -cp out kvstore.worker.WorkerLauncher 12.34.56.78 5000

  4개 Worker Thread가 한 프로세스 안에서 동시에 뜨며, 자동으로
  Master에 접속 후 작업을 받기 시작한다.

- Worker 실행 위치 : 조원 로컬 PC (4개 Worker Thread가 한 프로세스에서 실행)
- Master의 IP/포트는 실행 시 커맨드라인 인자로 지정 (3장 참고)
- 실행 순서 : Master를 먼저 실행해 대기 상태로 만든 뒤, Worker를 실행
- 주의 : 학교/회사 등 관리형 네트워크(방화벽)에서는 표준 포트(80/443) 외
  임의 포트로 나가는 연결이 막혀 있을 수 있으므로, Worker 실행은
  가정용 네트워크나 모바일 핫스팟 등에서 테스트할 것을 권장

5. 동적 작업 분배 알고리즘 설명 (WorkloadScheduler.java)
--------------------------------------------------------------------

[알고리즘] Least Queue First (최소 큐 우선)

Master가 각 Worker의 큐 크기를 계속 추적하다가(Worker의 QUEUE 보고 +
작업 전송 직후 낙관적 +1), 매번 "추적된 큐 크기가 가장 작은 Worker"에게
다음 작업을 보낸다. 전부 10/10이면 해당 작업을 최우선 큐로 되돌리고
잠시 대기한다. 실패로 재할당된 작업도 동일한 알고리즘을 타되,
priorityQueue가 항상 pendingQueue보다 먼저 소비되므로 순서상
최우선권만 가진다.

[장점]
  - 구현이 단순하고 이해하기 쉬움
  - 4개 Worker의 큐 깊이가 항상 거의 고르게 유지됨 (Join-the-Shortest
    -Queue는 큐잉 이론에서도 검증된 효과적인 로드밸런싱 방식)
  - Worker가 실제 보고한 큐 상태를 실시간으로 반영 (정적 라운드로빈이
    아님)
  - "낙관적 +1" 덕분에 Worker의 QUEUE 보고가 늦게 와도 한 Worker에게
    몰아 보내는 것을 방지

[단점]
  - 이 방식이 워낙 균형을 잘 맞추다 보니, 역설적으로 한 Worker에
    부하가 쏠리는 상황 자체가 거의 안 생겨서 P2P 부하분산이
    트리거될 기회가 매우 적음
  - 4개 Worker의 실제 처리 속도는 전혀 고려하지 않고 오직 "대기 중인
    개수"만 봄 (Worker마다 실제 처리 성능이 다르면 최적이 아닐 수 있음)
  - 분배 로직이 Master 단일 스레드에서 순차 처리되므로, Worker 수가
    훨씬 많아지면 병목이 될 수 있음 (현재 규모 4개에서는 문제없음)

6. P2P 부하 분산 알고리즘 설명 (WorkerThread.java)
--------------------------------------------------------------------

[알고리즘] 첫 번째로 발견한 여유 Peer에게 절반 이전

1) 내 큐 크기 x 평균 처리시간(2초) = 예상 대기시간. 15초를 넘으면
   (큐 8개 이상) 부하분산 트리거
2) 자신의 VirtualClock 기준 1~3초 랜덤 주기로 이 체크를 반복 수행
3) peer들을 포트 번호 순서대로 P2P_QUERY로 조회하여, 나보다 큐가
   적은 첫 번째 peer를 찾음 (가장 여유로운 peer를 찾는 게 아니고
   라운드로빈도 아님)
4) (내 큐 - peer 큐) / 2 만큼, 큐 뒤쪽(가장 늦게 처리될 예정인)
   작업부터 이전
5) peer가 그 사이 다 못 받아주면(레이스 컨디션) 못 받은 만큼 내
   큐로 롤백 -> 유실 없음

[장점]
  - Master 개입 없이 Worker끼리 자율적으로 처리 -> Master 부담
    감소, 완전히 분산된 구조
  - "첫 번째로 발견한 여유 peer"라 판단이 빠름 (조건 만족하는 순간
    바로 결정, 모든 peer를 다 비교할 필요 없음)
  - 큐 뒤쪽부터 이전해서, 곧 처리될 작업까지 건드려 오히려 지연을
    키우는 것을 방지
  - 질의-전송 사이의 레이스 컨디션까지 롤백으로 방어하여 작업 유실이
    원천적으로 불가능

[단점]
  - "가장 여유로운 peer"가 아니라 "포트 순서상 처음 만난 여유 peer"라,
    최적 분산은 아닐 수 있음
  - 조회(P2P_QUERY)와 실제 전송(P2P_TRANSFER)이 별도의 왕복 통신이라,
    그 사이에 상황이 바뀔 여지가 있음 (다만 롤백으로 안전하게 처리됨)
  - 점검 주기(1~3초, VirtualClock 기준)라 이 Worker 자신이 얼마나
    바쁜지(가상 시간이 얼마나 빨리 쌓이는지)에 따라 실제 점검 빈도가
    달라짐

7. 장애 처리(Fault Tolerance) 메커니즘 설명
--------------------------------------------------------------------

모든 작업은 처리될 때마다 80% 성공 / 20% 실패로 랜덤 판정된다.
실패하면 Worker가 RESULT=FAIL을 Master에 보내고, Master는 그 key를
KVStore의 priorityQueue(최우선 큐)에 등록한다. 이 큐는 다음 작업을
꺼낼 때(nextPendingKey) 항상 일반 대기열보다 먼저 소비되므로, 다음
분배 시 최우선으로 재할당된다. 재할당된 작업도 동일한 Least Queue
First 알고리즘을 타고, 동일한 80/20 규칙이 다시 적용된다. 성공할
때까지 이 과정이 반복되므로 이론상 데이터 유실은 없다.
reassignCount는 이 "FAIL로 인한 재할당"만 카운트한다 (큐가 꽉 차서
잠깐 미뤄진 것은 별도로 취급, 카운트하지 않음).

[장점] 실패해도 결국 100% 완료를 보장 (성공 확률 80%이므로 평균
1.25회 만에 성공), 별도의 복잡한 재시도 정책 없이 기존 분배 큐를
재사용해서 구현이 단순함

[단점] 이론상 매우 낮은 확률로 같은 작업이 여러 번 연속 실패할 수
있음 (지수 백오프나 최대 재시도 횟수 제한은 없음, 다만 80% 확률이라
실질적으로 문제 되는 수준은 아님)

8. 추가 구현 사항 및 기타 언급할 내용
--------------------------------------------------------------------

- Worker 자기 정체 확인(REGISTER) : Master가 접속 순서만으로
  workerId를 매기면 로그의 Worker 번호와 실제 물리 Worker가 어긋날
  수 있어서, Worker가 접속 직후 자기 workerId를 명시적으로 알려주는
  핸드셰이크(REGISTER 메시지)를 추가함
- 비정상 접속 방어 : Master가 공인 IP(AWS)에 떠 있으면 포트 스캐너
  같은 엉뚱한 접속이 들어올 수 있어서, 접속 후 5초 안에 정상 등록
  메시지가 안 오면 그 연결만 버리고 계속 대기하도록 처리
- 콘솔 로그 색상 : STATUS별로 터미널 출력에만 색을 입힘 (SUCCESS
  녹색 / FAIL 빨강 / WARN 노랑 / INFO 청록) - 제출용 .txt 파일에는
  영향 없음 (색상 코드가 섞여 들어가지 않음)
- VirtualClock 설계 : Master/Worker가 서로 다른 프로세스라 시계를
  물리적으로 공유할 수 없어, 메시지마다 clock 필드를 실어 보내고
  받는 쪽이 (Lamport Clock과 같은 방식으로) 더 큰 값을 채택하는
  느슨한 동기화 방식을 사용
